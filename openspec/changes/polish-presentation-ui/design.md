## Context

`SlidePreview` (`apps/bibletime/src/modules/presentation/components/slide-preview.tsx`) is the single component that renders a slide everywhere it appears: the projector output (`/present` route), the console's persistent `PreviewPanel`, the Bible picker's Preview column, and every `SlideCard` grid thumbnail. `SlideFrame` wraps it to letterbox/pillarbox the slide into a container that can flex in both dimensions, using `useSlideFit`'s `ResizeObserver`-driven `computeFit` (not CSS `aspect-ratio`, which doesn't resolve when both axes are already definite).

Because one component renders every surface, a single unconditional Tailwind class on its root — `ring-1` (`slide-preview.tsx:137`) — is responsible for both of the visual bugs reported (white/light border, and left/right clipping in previews): `ring-1` has no explicit color, so it resolves to the theme's `--color-ring` token (`oklch(0.708 0 0)` light theme, `oklch(0.556 0 0)` dark theme — both mid-to-light gray), rendered via `box-shadow`. A `box-shadow`-based ring paints outside the element's border box by default. When `computeFit` sizes the slide to exactly fill the container's width (a portrait-ish or exactly-16:9 container, i.e. pillarboxed top/bottom only, no side margin), the ring has no room to render on the left/right — it gets cut off by the container's `overflow-hidden` exactly at the edges, while the same ring is fully visible top/bottom where the letterbox bars give it room. That reads as "always cropped on the sides" while also being "a border I don't want" — one bug, two symptoms.

Separately, the reference line (`slide-preview.tsx:177-188`) is pinned to Tailwind's `text-sm` (a fixed 0.875rem), never multiplied by the `scale`/`fitScale` the body text (`textStyle.fontSize = template.fontSize * scale`) already uses — so it doesn't grow with the body text and looks mismatched at any resolution other than the one `text-sm` happens to look right at. The Bible version's human-readable label (`local_abbreviation`, e.g. `"RV1960"`, present on `BibleVersionCatalogEntry`/`BibleVersionSummary`) is never carried past `BiblePickerPanel` — `BiblePassageItemData` only stores a numeric `versionId`, and `resolveFolderItemContent` forwards just `text`/`reference` into the `SlidePreview` props, so there is currently no code path that could render it even if the reference were fixed.

Finally, the Preview column's "Convert to Slide" button (`bible-picker-panel.tsx:261-263`) calls `onAddVerse`, which only appends the item to the open Library folder — it never touches `setLiveSlide`/`window.open("/present", ...)`, the pair that `preview-panel.tsx`'s "Send to output" button already uses to push a slide to the projector window. The same gap exists one step later in the flow: `SlideCard` (`slide-card.tsx:61-74`), the grid tile for a slide already added to the open folder, only wires a single `onClick` (through `SlideConsole` to `console-view.tsx`'s `onSelectItem` → the console store's `selectItem`) that selects the item so `PreviewPanel` shows it — the user still has to then click "Send to output" separately.

## Goals / Non-Goals

**Goals:**
- Every slide render (output + all preview surfaces) has no unintended visible border/ring, and is never clipped on its left or right edge inside its fitted container.
- The on-slide reference visually scales in lockstep with the scripture text and gains an adjacent, lighter-weight Bible version label.
- The Bible picker's Preview column offers a one-click "Present" action (convert + immediately show on output) alongside the existing "Convert to Slide", and double-clicking a verse in the Bible reader does the same.

**Non-Goals:**
- Redesigning the slide template schema's selectable properties (e.g. exposing reference size as a user-configurable template field) — the reference will derive its size from existing template fields, not gain a new editable setting.
- Building a general "recently presented" history or undo for the new Present action.
- Changing how songs/media/announcements render — only the Bible-passage path is touched for the version-label threading (the reference/ring/crop fixes apply to `SlidePreview` generally, so they benefit those content types too, but no song/media-specific behavior is added).
- Touching the drag/drop or reordering behavior of Library folder items.

## Decisions

**1. Remove the base `ring-1` from `SlidePreview` rather than special-casing it per call site.**
No call site was found intentionally relying on this ring (grep confirms the only other `ring-*` usages in the codebase are explicit, purposeful selection/hover states in `template-manager.tsx`, `template-editor.tsx`, and `verse-picker-list.tsx` — all unrelated to `SlidePreview`'s own root). Deleting it from the shared component fixes the projector output, both preview panes, and every thumbnail in one place, and removes the clipping side-effect described above. If a future call site wants a selection outline around a `SlidePreview`, it can pass one via the existing `className` prop — the component's `cn(...)` merge already supports this.

**2. Also make the Electron projector window frameless.**
`apps/desktop/src/main.ts`'s present window (`setWindowOpenHandler`, ~line 365-382) sets `backgroundColor: "#000000"` and `autoHideMenuBar: true` but never sets `frame: false`, so the OS's native title bar/frame still wraps the output window. This is a second, independent source of an unwanted "border" around what's being presented (most visible on Windows, where the title bar is light by default). Fix by adding `frame: false` to that `BrowserWindow` constructor call. Low risk: this window is never meant to show chrome (it's driven entirely by the app; there's no title or window controls a user needs).

**3. Match the reference's `fontSize` exactly to the body text's; append the version label as a separate, lighter-weight inline span at that same size.**
The user's own framing of the bug — "the font size of the Bible verse (i.e., the book name) isn't the same as that of the text" — calls for equal size, not merely a proportional-but-smaller one. Change the reference's inline `fontSize` from the implicit `text-sm` class to `textStyle.fontSize` (the exact same computed value, `template.fontSize * scale`, the body `<p>` already uses), so reference and body are always identical in size and scale together. Render the version label as a second `<span>` inside the same reference `<p>`, sharing that same `fontSize`, with a lighter `fontWeight` (`300`) than the reference span (`500`) — separated from the reference text by a space, e.g. `Genesis 1:1 RV1960` with only `RV1960` in the lighter weight. This keeps the "displayed" crossfade logic (`displayed.reference`) working unchanged since the version label rides along as part of the same content swap already tracked by that state.

**4. Thread the version abbreviation through the data model as a plain string, not a re-lookup by id.**
Add `versionAbbreviation?: string` to `BiblePassageItemData` (alongside the existing `versionId?: number`, which stays for any future need to re-resolve the full version) and to `LiveSlidePayload`, populated at add-time in `BiblePickerPanel.handleConvert` from `selectedVersion?.local_abbreviation`. This avoids `resolveFolderItemContent` or the `/present` route needing to re-fetch/lookup a `BibleVersion` at render time — the label is captured once, same pattern as `reference` and `text` already being captured at add-time rather than re-derived. `resolveFolderItemContent` forwards it alongside `text`/`reference` into the `SlidePreview` props (new optional `versionLabel` prop).

**5. Fix cropping by removing the ring (Decision 1) rather than restructuring the container nesting.**
The double `overflow-hidden` nesting (`SlideFrame`'s own container + the panel's outer wrapper) was considered as an alternative root cause, but the fitted width/height are measured directly off the innermost container's own `ResizeObserver` entry — nothing in that chain adds unaccounted padding or border that would explain a consistent left/right clip independent of the ring. Removing the ring is expected to resolve the reported clipping; the implementation step includes a manual visual check (present view + both preview panes, several aspect ratios) to confirm before considering this decision closed, since the ring was a hypothesis derived from code reading, not a screenshot diff.

**6. Add "Present" as a second button next to "Convert to Slide", and reuse the existing convert + send-to-output primitives directly.**
`BiblePickerPanel` already computes everything `handleConvert` needs (`pendingText`, `pendingReference`, `effectiveTemplate`, `selectedVersion`). Add a `handlePresent` that calls the same conversion logic as `handleConvert` (so the verse is still recorded in the open folder — the user should end up with the same folder state as clicking "Convert to Slide" — the proposal explicitly calls this "converts the slide and immediately presents it") and then, using the same data already in scope, calls `setLiveSlide({ text: pendingText, reference: pendingReference, template: effectiveTemplate })` followed by `window.open("/present", "bibletime-present")` — the identical pair `preview-panel.tsx`'s "Send to output" button already calls, so no new present-triggering mechanism is introduced. Disable this button under the same `canConvert` condition as "Convert to Slide".

**7. Double-click on a verse row triggers the same convert-and-present path, computed from the clicked verse directly rather than through `pendingVerseNumber` state.**
`VersePickerList`'s verse button (`verse-picker-list.tsx:74-88`) currently only has `onClick={() => onSelectVerse(verseNumber)}`. Since `handlePresent` depends on `pendingText`/`pendingReference`, which derive from `pendingVerseNumber` via a state update that isn't synchronously available, double-click cannot just call `onSelectVerse` then immediately read stale `pending*` values. Instead, add an `onDoubleClick` prop threaded down to `VersePickerList`, which `BiblePickerPanel` implements by resolving text/reference for the double-clicked verse number directly (same `findVerseText`/reference-string construction already used to compute `pendingText`/`pendingReference`, just parameterized by the clicked verse number instead of the pending one) and then running the same convert-and-present steps as `handlePresent`. This also updates `pendingVerseNumber` to the double-clicked verse so the Preview column reflects what was just presented.

**8. Double-click on an existing slide card presents it directly, reusing the already-resolved content instead of re-deriving it.**
`SlideCard` already calls `resolveFolderItemContent(item, templates)` (`slide-card.tsx:40`) to get the exact `{ text, reference, template }` it renders — this is the same shape `PreviewPanel`'s "Send to output" button already sends via `setLiveSlide`. Add an `onDoubleClick` prop to `SlideCard`, fired from the same clickable `div` that currently only has `onClick`/`onKeyDown` (`slide-card.tsx:61-70`), threaded through `SlideConsole` (which already forwards `onSelect` per-card the same way) up to `console-view.tsx`. There, implement `onPresentItem(itemId)`: look up the item in `openedFolder.items`, call `resolveFolderItemContent` on it (same helper `PreviewPanel` uses), then `setLiveSlide({...})` + `window.open("/present", "bibletime-present")` — no new present-triggering mechanism, just the third call site for the existing pair. Also call the existing `onSelectItem`/`selectItem` for that id first, so `PreviewPanel` and the grid's selection border stay in sync with whatever was just presented (matching how single-click selection already behaves, and consistent with Decision 7's verse-list double-click also updating `pendingVerseNumber`).

## Risks / Trade-offs

- [Removing `ring-1` could regress an intentional visual affordance in some undiscovered call site] → Mitigation: grep-confirmed no other consumer depends on `SlidePreview`'s own ring; all other `ring-*` usages in the codebase are separate, explicit classes on unrelated elements. A visual pass over every `SlidePreview`/`SlideFrame` call site (output, both preview panes, template manager thumbnails, slide cards) is part of the implementation tasks.
- [Making the reference identical in size to the body text could look heavy/oversized for very long references or verse text combinations] → Mitigation: not treated as a blocking risk — matches the user's explicit correction that reference and body should be "the same" size; revisit only if a specific template/content combination is reported as looking wrong.
- [Frameless present window (`frame: false`) could change window-manager behavior per OS (e.g. losing the ability to move/close it via a title bar)] → Mitigation: the window is opened programmatically and closed by closing/reusing the same named window (`window.open` with a fixed name); it isn't meant to be manually repositioned. Verify on the desktop build that closing the app or the source window still tears down the present window correctly.
- [Double-click convert-and-present duplicates handler logic already in `handleConvert`/`handlePresent`] → Mitigation: extract the shared "resolve text/reference/template for a given verse number, then convert+present" logic into one function both the button handler and the double-click handler call, rather than copy-pasting it.
- [Adding a second folder item on every double-click could surprise a user who only meant to preview] → Mitigation: this matches the proposal's explicit instruction ("this should also happen if I double-click the Bible text") — flagged here so it's a conscious, not accidental, behavior choice.
- [`SlideCard`'s double-click could conflict with its existing drag-and-drop reordering] → Mitigation: not a real risk here — `useSortable`'s drag listeners are only attached to the small grip handle button above the card (`slide-card.tsx:51-59`), not the card body itself, so the card body's `onClick`/`onDoubleClick` never compete with a drag gesture.

## Migration Plan

No data migration: `versionAbbreviation` is a new optional field on an existing interface (`BiblePassageItemData`), so previously-saved folder items without it simply render without a version label (falls back to omitting the label span, matching current behavior). No feature flag needed — this is a UI-only, additive and corrective change, verified visually in the running desktop app before considering the change complete.

## Open Questions

- None outstanding — the reference now matches the body text's font size exactly (per user correction), and the version label's weight delta (`300` vs. the reference's `500`) was resolved during implementation.
