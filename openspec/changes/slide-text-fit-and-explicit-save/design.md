## Context

`SlidePreview` (`apps/bibletime/src/modules/presentation/components/slide-preview.tsx`) renders verse text at `template.fontSize * scale` inside a `overflow-hidden` box, where `scale` is only ever the *responsive* fit factor (from `useSlideFit`'s `REFERENCE_WIDTH = 1920`-relative measurement, or a caller-supplied constant like a thumbnail's `0.32`). Nothing measures the text's own rendered height against the box, so a verse long enough to wrap past the box's height just gets its overflow clipped — invisibly, with no indication to the user. This happens identically in the template editor's own preview, the console's live preview (`SlideFrame`), and the real `/present` projector output, since all three render through the same `SlidePreview`.

Separately, `apps/bibletime/src/routes/templates/$templateId.tsx` currently autosaves: every `TemplateEditor` `onChange` and the name `Input`'s `onBlur` call `useTemplates().update()` directly, matching this app's general "everything autosaves" convention (see `routes/templates/new.tsx`'s comment). The user has asked for this one page specifically to move to an explicit save model instead, plus add the delete action that today only exists in the template gallery (`TemplateManager`).

This builds directly on the already-applied `redesign-template-builder-layout` change (two-pane console: left options rail, right live preview) — the route/component structure below assumes that layout exists.

## Goals / Non-Goals

**Goals:**
- Verse text is never invisibly clipped: it shrinks (down to a floor) to stay fully visible inside whatever box it's rendered in, everywhere `SlidePreview` renders real text.
- A verse too long even for the auto-fit floor can be manually split into multiple slides from the Bible picker, in one action.
- The template editor holds edits locally and only writes to storage on an explicit "Save" click; "Delete" (with confirmation) and "Restablecer plantilla" (now acting on the draft) live alongside it; navigating away with unsaved changes is guarded.

**Non-Goals:**
- No auto-*growing* text past the authored `fontSize` — a short verse in a huge box still renders at exactly the authored size, never larger.
- No NLP-grade sentence splitting for the split feature — a punctuation-aware heuristic, not a language-aware parser.
- No change to the autosave convention anywhere else in the app (Bible reader, library folders, settings, etc.) — this explicit-save model is scoped to the template editor page only.
- No change to `TemplateManager`'s gallery-card duplicate/export/delete actions — those keep working exactly as today, independent of the editor's new draft model.

## Decisions

### Auto-fit text sizing

- **Measurement lives inside `SlidePreview` itself**, not pushed onto callers. `SlidePreview` already owns `textRef`/`referenceRef`; add a root-box ref and a new hook, `useAutoFitFontScale`, in `use-slide-fit.ts` (a sibling to `useSlideFit`/`useElementWidthScale`, same `REFERENCE_WIDTH` conventions). It takes the box ref, the text ref, and the *nominal* font size (`template.fontSize * scale`) and returns an additional `autoFitScale` (0 < autoFitScale ≤ 1) applied on top: final font size = `template.fontSize * scale * autoFitScale`. Callers (`SlideFrame`, `TemplateEditor`'s route, thumbnails) need no changes — auto-fit is transparent.
- **Algorithm: binary search, not a linear shrink loop.** On text/template/box-size change (a `ResizeObserver` on the box plus a `useLayoutEffect` keyed on the text content and nominal size), binary-search `autoFitScale` between a floor and `1.0` (≈6-7 iterations to a reasonable precision) by measuring the text node's `scrollHeight` against the box's available content height at each candidate scale. Chosen over a linear step-down loop because this measurement can run for many simultaneously-rendered thumbnails (a folder grid, the template gallery) — fewer iterations matters more there than in the single editor preview.
- **Floor**: a `MIN_AUTOFIT_FONT_PX` constant (18px, in reference-canvas terms) below which text stops shrinking further and instead is left to clip as it does today — this is the signal to the user that a verse is a genuine "split into slides" candidate, not something auto-fit should paper over indefinitely. `autoFitScale` floor = `MIN_AUTOFIT_FONT_PX / (template.fontSize * scale)`, clamped so it's never above `1` (a tiny nominal size just means the floor never kicks in).
- **Alternative considered**: doing this measurement one level up, in `SlideFrame`/`useSlideFit`, since that's where box-fitting already happens. Rejected because the editor's own preview (`$templateId.tsx`) renders `SlidePreview` directly (via CSS `aspect-ratio`, not `SlideFrame`) — auto-fit needs to work there too, so it has to live where every call site already converges: inside `SlidePreview`.

### Manual slide splitting

- **Split point selection: punctuation-nearest-to-midpoint, word-boundary fallback.** For N slides, compute N-1 target midpoints across the text's character length; for each, search outward from the target for the nearest clause-ending punctuation (`,`, `;`, `:`, `.`, `…`) and split there (after the punctuation and any following space); if none exists within a reasonable window, fall back to the nearest whitespace so a split never lands mid-word. Chosen over a fixed-length or pure word-count split because it keeps each resulting slide's text grammatically coherent, which matters more for a spoken/read verse than perfectly even slide lengths.
- **UI**: a small split-count control (a `Select` with values 2–5, default 2) plus a "Dividir en diapositivas" button, placed in the Bible picker's Preview column next to the existing "Convertir a diapositiva" button, gated by the same `canConvert` (a verse is pending) condition. Each resulting `BiblePassageItemData` reuses the verse's `bookUsfm`/`chapterUsfm`/`verseNumber`/`versionId`/`versionAbbreviation`; `reference` gets a part suffix, e.g. `"Génesis 1:1 (1/3)"`, so the folder grid and preview panel show which piece of the verse each slide holds.
- **Folder write: one atomic call, not N sequential ones.** Add `addItemsToFolder` (plural) to `use-library.ts`, appending an array of items and writing to storage once — `addItemToFolder` (singular) stays as-is for every other call site. `BottomDrawer`/`BiblePickerPanel` gain a parallel `onAddVerses` prop; `console-view.tsx` wires it to `library.addItemsToFolder`.

### Explicit save / delete / discard

- **Local draft state, dirty-checked with `JSON.stringify`.** `$templateId.tsx` holds `draftName`/`draftTemplate` state (the existing `name` state generalizes to this). `isDirty = draftName.trim() !== existing.name || JSON.stringify(draftTemplate) !== JSON.stringify(existing.template)`. `SlideTemplate` is plain JSON-safe data (no functions/dates/Maps), so string comparison is exact and correct — simpler than writing/maintaining a structural deep-equal for a nested-but-plain shape that changes shape occasionally (new template fields). Draft resets to match `existing` whenever `existing.id` changes (navigating to a different template) or immediately after a successful Save.
- **Save** calls `update(existing.id, { name: draftName.trim(), template: draftTemplate })` — the first time `name` and `template` commit together in one call, rather than name-on-blur and template-per-field as today. Disabled when `!isDirty`.
- **Delete** opens a confirmation `Dialog`, reusing `ProjectList`'s existing pattern (`Dialog`/`DialogHeader`/`DialogTitle`/`DialogDescription`/`DialogFooter`, a `destructive`-variant confirm button) rather than a new component or a raw `window.confirm` — this app already has one delete-confirmation convention, and this reuses it. On confirm: `remove(existing.id)`, then navigate to `/library` (same destination as the back button), since the template no longer exists to keep showing.
- **"Restablecer plantilla" now sets the draft to `DEFAULT_SLIDE_TEMPLATE`**, not an immediate `update()` call — it becomes just another draft edit, requiring Save like any other change, consistent with "no more editor calls write straight through."
- **Unsaved-changes navigation guard**: `useBlocker({ shouldBlockFn, enableBeforeUnload, withResolver: true })` (the modern object-options form, confirmed in the installed `@tanstack/react-router`'s `useBlocker.d.ts`), resolved through a confirmation `Dialog` (same reused pattern) for in-app navigation. `enableBeforeUnload` covers the tab-close/reload case natively via the same hook — no separate manual `beforeunload` listener needed.
- **Alternative considered** for dirty-tracking: comparing individual fields instead of whole-object JSON — rejected as unnecessary complexity; the whole-template Save call already writes every field regardless of which one changed, so the coarser check is sufficient and simpler.
- **A never-saved template (`/templates/new`'s auto-created record) is tracked separately from `isDirty`'s normal field-diff check, via a `hasSavedOnce` flag** seeded from a `?isNew=true` search param that `/templates/new` attaches to its redirect. Revised after live testing surfaced a real gap: `/templates/new` persists a record immediately, so a user who opened "New" and immediately backed out with zero edits saw no warning and left a permanent empty "New template" entry in the gallery, and the top-right action read "Delete" for something that, from the user's perspective, was never saved. Fix: `isDirty` is `!hasSavedOnce || <normal diff>` (so a never-saved template is always treated as dirty, even with zero edits), the button reads "Cancel" instead of "Delete" while `!hasSavedOnce`, and both the button and the unsaved-changes guard's discard action call `remove()` on confirm — actually deleting the stub, not just navigating away from it. `hasSavedOnce` flips to `true` on the first successful Save. `handleDuplicate` deliberately does not set `?isNew` — a duplicated template already has real, intentional content, so it should read as "Delete" immediately, not "Cancel".
- **Clearing `?isNew` after the first Save uses `window.history.replaceState` directly, not `navigate()`.** `Route.useSearch()` needs the URL's `isNew` gone by the next reload (otherwise `hasSavedOnce` would reset to `false` again on every reload of an already-saved template) — but calling `navigate({ to: sameRoute, params: sameParams, search: () => ({}) })` was a confirmed no-op in the installed `@tanstack/react-router`: it neither updated `window.location` nor rejected, even though the corresponding `shouldBlockFn`/handler code path visibly ran (verified with direct console logging). Likely cause: the router treats a navigation to the same matched route+params as a no-op regardless of a differing search payload. `history.replaceState(history.state, "", location.pathname)` sidesteps the router entirely for this cosmetic URL cleanup — safe here specifically because nothing else needs the router to be aware of the change; only a *future reload* needs to see the corrected URL, and preserving `history.state` as-is avoids corrupting whatever the router had stored there.

## Risks / Trade-offs

- [Binary-search auto-fit runs a measurement effect on every text/box change, including in a folder grid full of `SlidePreview` thumbnails] → Bounded iteration count (~6-7) and only re-runs when text/template/box size actually changes (not on unrelated re-renders), keeping it cheap even across many simultaneous thumbnails.
- [Punctuation-nearest-to-midpoint splitting can still produce an awkward split for verses with little internal punctuation (e.g. a long unbroken clause)] → Falls back to nearest whitespace so a split is never mid-word; genuinely punctuation-free long verses are rare enough that this is an acceptable rough edge for a manual, user-triggered action (not silently automatic).
- [Explicit save is a real behavior change from this app's otherwise-universal autosave convention, and could surprise a user used to the old behavior] → Scoped to just this one page per the user's explicit ask; the unsaved-changes guard (in-app blocker + `beforeunload`) is the safety net that prevents silent data loss, which is the main risk autosave was protecting against.
- [`useBlocker`'s exact API shape (legacy vs. `withResolver`) needs to be checked against the installed `@tanstack/react-router` version at implementation time] → Confirmed present in `node_modules` during this design; implementation should read `useBlocker.d.ts` directly rather than assuming a specific overload's shape from memory.
