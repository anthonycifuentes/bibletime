## Context

`Folder` (`apps/bibletime/src/modules/library/interfaces/index.ts:49-56`) is flat today: `{ id, projectId, name, items, createdAt, updatedAt }`, no `parentId`, no ordering field. `LibraryStorageDriver` (`:63-68`) exposes only `list`/`save`/`remove` — one whole `Folder` record per call, no batch/reorder primitive. Two driver implementations exist: `web-library-storage.ts` keeps every folder as one array under a single `localStorage` key (read-all → filter-out-by-id → append → write-all on every save), and the desktop driver (`apps/desktop/src/main.ts`) keeps one JSON file per folder under Electron's userData dir, listed via `fs.readdir` (enumeration order not guaranteed stable). Since neither driver has ever supported an explicit order, "display order" today is an accident of storage, and both are equally capable of storing two new plain fields on `Folder` with zero interface changes — this is purely additive at the storage layer.

`use-library.ts` (164 lines) already has a mutation pattern to crib from: `reorderFolderItems(folderId, itemIds)` (`:121-133`) takes a fully-ordered id array and rewrites one folder's `items` in a single `save`. There is no folder-level equivalent — `createFolder`/`renameFolder`/`deleteFolder` are the only folder mutations, none touching position or parentage.

`FolderTree` (`folder-tree.tsx`, 237 lines) renders a flat `folders.map(...)` — each folder a `Collapsible` (chevron rotates on open, `CollapsibleContent` shows read-only item rows). Its expand/collapse state is driven entirely by `openFolderId === folder.id` — clicking a folder row both opens it in the console *and* expands its row in the tree, a single source of truth the user has explicitly chosen to keep as-is (a prior attempt to split "expand" from "open in console" into separate state was reverted this session). No `@dnd-kit` usage exists in this file today.

`@dnd-kit/core@^6.3.1` + `@dnd-kit/sortable@^10.0.0` + `@dnd-kit/utilities@^3.2.2` are already dependencies, already wired up identically (flat `SortableContext` + `rectSortingStrategy` + `arrayMove` + `PointerSensor`) in `slide-console.tsx` for reordering slide cards within one open folder. dnd-kit ships no first-party "tree" preset, but its own documented pattern for nested/tree drag-and-drop is well-established (flatten the visible tree into one ordered list, track each node's parent, use `onDragOver`/`onDragEnd` to compute reparenting) — this is the pattern this design adopts, rather than introducing a second drag-and-drop library. `@atlaskit/pragmatic-drag-and-drop` was evaluated as the leading lightweight alternative (its official Tree example is close to a 1:1 match for a Notion-style nested folder tree, and its raw bundle is smaller than dnd-kit's combined packages) but was rejected: it would mean two DnD libraries with two different mental models living in one small app, which costs more in maintenance surface than it saves in kilobytes — dnd-kit is already paid for and already understood.

## Goals / Non-Goals

**Goals:**
- Folders can be nested up to 3 levels deep (root, subfolder, sub-subfolder) under a folder in the same project.
- Dragging a folder row reorders it among its current siblings, or reparents it under another folder if dropped onto that folder's row (subject to the depth cap and cycle prevention).
- Slides can also be dragged in the sidebar tree — reordered within their folder, or moved into a different folder (dropped onto one of that folder's own slides for a precise position, or onto the folder's own row to append at the end).
- "New subfolder" is available from a folder's context menu, disabled once that folder is already at the deepest allowed level.
- Deleting a folder deletes its entire subtree (cascading), matching the existing single-folder delete's no-confirmation behavior.
- Clicking an already-open folder closes it (a real toggle), not just "clicking any folder always opens it."
- Zero new npm dependencies.

**Non-Goals:**
- Unlimited/arbitrary nesting depth — 3 levels is a hard cap, not a configurable setting.
- Cross-project drag-and-drop (a folder or slide can only move within the same `projectId`).
- Changing how the *console's own grid* (`slide-console.tsx`/`SlideCard`) reorders slides — untouched; the sidebar tree's slide drag added here is a separate, independent interaction living entirely in `folder-tree.tsx`'s own `DndContext`.
- Re-litigating the reverted expand/collapse-vs-open-in-console split — this design keeps that single-source-of-truth behavior and only extends it (see Decision 4).
- A confirmation dialog before delete — neither the current single-folder delete nor this cascading version gets one; that's a separate, unrelated UX change if ever wanted.
- Multi-select drag (dragging several folders or slides at once) — one item dragged at a time, same as the existing slide-card drag.

## Decisions

**1. Add `parentId: string | null` and `position: number` to `Folder`; no stored `depth` field.**
`parentId: null` means root-level. `position` is a sibling-scoped sort key (integer, unique only within its `(projectId, parentId)` group) — needed because, per the Context section, storage order was never reliable and drag-reordering now requires the user's chosen order to persist deterministically. Depth is deliberately *not* stored: it's derived at read time by walking the `parentId` chain (or during tree-building, by recursion level), so reparenting a folder never requires updating a stale `depth` value on every descendant — only `parentId` and `position` ever change on a move, keeping writes minimal (see Decision 3).

**2. No migration script — treat missing fields as defaults at read time.**
Existing folders (saved before this change) have `parentId: undefined` and `position: undefined` in storage. The tree-building helper (Decision 5) normalizes `parentId ?? null` and falls back to the existing array-index (or `createdAt`) when `position` is missing, so old data renders as a flat, stably-ordered root list — exactly today's behavior — without a one-time migration pass. The first drag the user performs on any of those folders assigns them real `position` values going forward.

**3. `moveFolder(folderId, newParentId, newIndex)` mirrors `reorderFolderItems`'s "rewrite the full order" pattern, adapted for folders being separate storage records.**
Unlike `reorderFolderItems` (one document, one array field, one `save`), folders are independent records in both drivers, so a move touches multiple documents: the moved folder (new `parentId` + `position`), plus every other folder in whichever sibling group(s) shift position (the new parent's children, and — if the parent changed — the old parent's remaining children too). The action:
1. Validates the move (Decision 6) — rejects and no-ops if invalid.
2. Computes the new ordered sibling list for the destination group (moved folder inserted at `newIndex`).
3. Re-numbers `position` sequentially (0..n-1) for that destination group, and separately for the origin group if the parent changed.
4. Calls `storage.save` once per folder whose `parentId` or `position` actually changed (typically a handful of small JSON writes — acceptable for a local, non-networked, small-n case; not wrapped in a transaction since neither storage driver supports one, matching the non-atomic nature every other multi-step mutation here already has).

**4. Expand/collapse stays keyed off `openFolderId`, extended to auto-expand ancestors of the open folder — but the click handler toggles on the *literal* open id, not the ancestor-inclusive expanded state.**
Per the user's explicit revert of a prior change that split "expand" from "open in console" into independent state, this design does not reintroduce separate expand state. A folder row is considered *expanded* (shows its children) if `folder.id === openFolderId` **or** `folder.id` is an ancestor of `openFolderId` (computed by walking up the open folder's `parentId` chain — derived, not stored) — needed so opening a level-2 subfolder reveals the path down to it. Clicking a row, however, toggles on `folder.id === openFolderId` specifically: clicking the currently-open folder closes it (`onOpenFolder(null)`); clicking any other folder — including one that's merely showing as expanded because a descendant is open — opens *that* folder instead. Conflating the click handler with the broader `isExpanded` check was an earlier bug: it made clicking an already-open folder a no-op (since `isExpanded` was true either way, `onOpenFolder(folder.id)` fired again with the same id), which read as "clicking again doesn't close it."

**4b. The whole row is the drag handle, not a separate grip button.**
Reworked after user feedback that a dedicated hover-only grip button was too easy to miss entirely — dnd-kit's `PointerSensor` `activationConstraint: { distance: 4 }` already distinguishes a stationary click from an actual drag, so `attributes`/`listeners` are attached to the row's own container. A plain click on the icon, name, or (for folders) the row itself still reaches the underlying button normally; only real pointer movement is intercepted as a drag. The rename `<input>` and the "..." dropdown trigger still call `stopPropagation` on `pointerdown`, since those specifically involve their own click-and-drag semantics (text selection; menu open state) worth insulating from the ambient row-level listener.

**5. A pure `buildFolderTree(folders)` helper produces the nested structure; `FolderTree` renders it recursively.**
New file `apps/bibletime/src/modules/library/lib/build-folder-tree.ts`: groups the flat `Folder[]` by `parentId` (`null` → root group), sorts each group by `position` (falling back to original array index for folders missing it, per Decision 2), and returns `{ folder: Folder; children: TreeNode[] }[]`. `FolderTree` recurses over this instead of `folders.map(...)`, indenting each level (e.g. `pl-4` per depth) and passing the current recursion depth down so "New subfolder" can be disabled at depth 2 (the deepest allowed — 0/1/2 is 3 levels).

**6. Depth cap and cycle prevention are enforced once, in `moveFolder` (and again, trivially, in "New subfolder"'s disabled state).**
Before persisting any move: reject if `newParentId === folderId` (self-parent), reject if `newParentId` is a descendant of `folderId` (walk down from `folderId`'s subtree — a cycle), and reject if the target depth (`newParentId`'s depth + 1`) exceeds 2. "New subfolder" in the context menu is simply hidden/disabled whenever `depth(folder) >= 2`, so most invalid states are prevented at the UI level before `moveFolder` is ever called; `moveFolder`'s own validation is the authoritative backstop for the drag-and-drop path, where the UI can't as easily pre-filter every possible drop target.

**7. Drag-and-drop interaction: flatten the *visible* rows into one `SortableContext`; distinguish "reorder" vs. "reparent" by vertical position within the hovered row, not by dnd-kit's official horizontal-offset depth projection. `collisionDetection` must be `closestCenter`, not dnd-kit's default.**
The official dnd-kit sortable-tree example projects a dragged item's new depth from *how far horizontally* the pointer has moved (indent/outdent by dragging sideways) — powerful, but noticeably more complex to implement and tune than this feature needs. Given the explicit "lightest and simplest way" mandate, this design instead splits each hovered row into vertical zones during `onDragOver`/`onDragEnd` (via the hovered row's measured `rect` from dnd-kit and the pointer's Y offset within it). The initial implementation used a 25/50/25 split and left `collisionDetection` unset (defaulting to dnd-kit's `rectIntersection`) — in practice this made reparenting (the large 50% middle zone) trivial but reordering siblings (the thin 25% edges) nearly impossible to hit, which is exactly the "nesting works, reordering doesn't" bug reported after the first pass. Two fixes:
   - `collisionDetection={closestCenter}` on the `DndContext` — the same override `slide-console.tsx`'s existing flat sortable list already uses, and for the same reason: `rectIntersection`'s literal-overlap requirement is unreliable for thin, tightly-packed rows.
   - Rebalanced zones to bias toward the more common action (reordering): a folder target now splits **35% before / 30% inside / 35% after**, giving sibling reordering a much larger, easier-to-hit target while nesting still only needs a deliberate hover near dead center. A slide target has no nesting concept at all — just a 50/50 before/after split.
   The flat list fed to `SortableContext` is the currently *visible* rows (folders and, per Decision 8, their slides) in display order — a folder can still be dropped "onto" a collapsed row's middle zone to nest inside it even though its children aren't currently shown, since that's a distinct gesture from reordering among visible siblings.

**8. Slides are draggable in the same `SortableContext` as folders, distinguished by id membership rather than a separate `DndContext`.**
Extending scope beyond the original proposal (which excluded slide reordering as a non-goal) per direct user request. Rather than running a second, parallel `DndContext` for slides, both folders and slide rows share one flattened `sortableIds` list and one set of drag handlers — `resolveDropZone`/`handleDragEnd` branch on `folderIds.has(id)` to tell which kind of thing is being dragged and dropped onto, since a folder id and a slide (`FolderItem`) id are drawn from disjoint id spaces already (`createId("folder")` vs `createId("item")`). This avoids a second sensor/context/activation-distance setup for what's otherwise the same gesture:
   - Dragging a **slide** onto another **slide** → reorder/move at that precise position (`moveFolderItem`), whichever folder the target slide belongs to (may differ from the dragged slide's current folder — this is how a slide moves to a different folder with a specific position, not just appended at the end).
   - Dragging a **slide** onto a **folder**'s own row → append to the end of that folder's items (`moveFolderItem(..., toFolder.items.length)`), regardless of which of the folder row's three zones is hovered (slides don't affect folder nesting/ordering).
   - Dragging a **folder** onto a **slide** row is rejected outright in `resolveDropZone` (a folder has nowhere to go relative to a slide) — checked before computing any zone, so no misleading drop indicator ever appears for that combination.
   `moveFolderItem(itemId, fromFolderId, toFolderId, newIndex)` (new `use-library.ts` action) mirrors `moveFolder`'s shape: same-folder is a single `save` (like `reorderFolderItems` but for one item's position); cross-folder is two `save`s (remove from origin, insert into destination) — the same non-atomic-but-acceptable multi-document write pattern as `moveFolder`.

## Risks / Trade-offs

- [Multi-document, non-atomic writes in `moveFolder` (Decision 3) could leave sibling `position` values inconsistent if a save fails partway (e.g. desktop filesystem write error mid-sequence)] → Mitigation: consistent with every other multi-step mutation already in this codebase (e.g. `deleteFoldersInProject` looping `deleteFolder`); an inconsistent partial reorder is a cosmetic issue (folders just re-sort oddly next load), not data loss — no folder or its items are ever deleted or corrupted by a failed reorder.
- [The three-zone (top/middle/bottom) hit-testing is a custom `onDragOver` calculation, not something dnd-kit provides out of the box] → Mitigation: this is a small, well-contained piece of arithmetic (compare pointer Y to the hovered rect's top/height), far simpler than adopting the full horizontal-projection algorithm dnd-kit's own tree example uses — acceptable complexity for the simplicity this feature calls for.
- [Cascading delete removes subfolders and their slides with no confirmation, same as today's single-folder delete] → Mitigation: intentionally matches existing behavior rather than introducing a new, inconsistent confirmation step only for folders-with-children; flagged here so it's a conscious choice, not an oversight.
- [Auto-expanding ancestors of `openFolderId` (Decision 4) means a user can no longer manually collapse an ancestor while its descendant is open] → Mitigation: matches the single-open-folder invariant already in place; if this proves annoying in practice it's a follow-up UX change, not a blocker for this one.
- [Existing folders lack `position`, so the very first render after this ships falls back to array/creation order (Decision 2), which may not match a user's mental model of "the order I've been seeing them in"] → Mitigation: that fallback order is not a regression — it's exactly today's already-arbitrary order — and the first manual drag on any folder fixes it permanently for that sibling group.
- [Only one folder's own slides are visible at a time (plus its ancestors', per Decision 4) — a slide can't be dragged directly to a precise position inside a sibling folder that isn't currently expanded] → Mitigation: dropping onto that sibling folder's own row still moves the slide there (appended at the end); reordering within it is then a follow-up drag once it's open. Not a blocker given the existing single-open-folder architecture; a bigger multi-expand tree is out of scope here.

## Migration Plan

No data migration and no feature flag: `parentId`/`position` are new optional-in-practice fields (all reads default them per Decision 2), so every existing project/folder continues to render exactly as it does today until the user performs their first drag or creates a subfolder. Rollout is just shipping the code — verified by running the app and confirming existing folders still list correctly before testing the new nesting/drag behavior on top.

## Open Questions

- None outstanding — the drag-zone thresholds (35/30/35) were tuned against real feedback that the initial 25/50/25 split made reordering nearly impossible; they may need further adjustment once used more, but no numeric value is left unresolved.
