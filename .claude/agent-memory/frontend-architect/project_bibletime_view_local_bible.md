`apps/bibletime` (package name "web", alias `@/*` -> `src/*`) is the shared codebase for both the web app and `apps/desktop` — the desktop shell just loads the web app's dev server/build in an Electron window, so anything built for the web app works for desktop with no extra wiring. This came from `openspec/changes/view-local-bible/design.md`; check whether `apps/desktop` still exists and still works this way before assuming it for future work, since this was true as of 2026-07-28 and openspec changes get archived after completion.

Before the `bible` module (the first real feature module in this app — every other module under `src/modules/*` was an `export {}` stub), there was no `QueryClientProvider` anywhere in the app despite `@tanstack/react-query` being a dependency. Added one at `src/modules/core/providers/query-provider.tsx` (client created via `useState` inside the component, not a module-level singleton, to avoid cross-request state leakage under TanStack Start SSR) and wired it into `src/routes/__root.tsx`. Verify this still exists before assuming query hooks work — if a future module's `useQuery` hooks throw about missing context, this provider may have been removed or moved.

See [[feedback-tanstack-start-routetree]] for the routing-generation gotcha hit while building this module's routes.

**2026-07-28 update — consolidated to a single route.** The module went through two rounds of route design: first 3 routes (`bible/index`, `bible/$bookUsfm/index`, `bible/$bookUsfm/$chapterUsfm`), then a four-column console still split across those 3 routes, then finally the user rejected page navigation entirely — "selecting a book must not navigate to another screen." Landed on exactly one route, `src/routes/bible/index.tsx`, with `book`/`chapter`/`verse` as optional `validateSearch` params; every selection calls `navigate({ to: "/bible", search: {...} })` changing only search params (never the path), so the route component never remounts. `validateSearch` only hardcodes the bare-URL default (Genesis 1, verse 1, when all three are absent) — resolving a *partial* state (e.g. only `book` set right after picking a new book) into "that book's first chapter" is done in the view (`bible-console-view.tsx`), not `validateSearch`, because that needs the loaded Bible data which isn't available synchronously when the URL is parsed. This pushed `BookList`/`ChapterNav` from `Link`-rendered `Button`s (`render={<Link/>}` + `nativeButton={false}`) to plain `onClick` callbacks owned by the view (`onSelectBook`/`onSelectChapter`), since the nav target is now dynamic search-param state, not a declarative route — also incidentally sidesteps the Base UI `nativeButton` gotcha for any button whose target becomes dynamic like this. If a future module needs multi-selection state that should update "in place" (no page transition), this same pattern (one route + optional search params + view-level fallback resolution) is the validated approach here — check whether `/bible` still looks like this before assuming it, since further changes may have moved on.
